# MH2 正式分组项登记表

本表是 MH2 可复用分组、标签和分群的唯一业务事实源。它回答三个问题：

1. 这个分组的业务含义和人口粒度是什么；
2. 在数数请求中能否作为 `eventView.groupBy` 使用，以及使用哪个原生元数据；
3. 在哪个日期/快照下有效，是否已有真实只读请求验证。

`data-analysis-agent` 只负责接受本表中 `READY` 项的 `groupBy` 元数据、调用既有分析 builder、保存请求/原始返回并验证结果。它不自行发明业务分组，也不把一个报表里的分档固化为通用标签。

稳定性验收的本地入口是 `F:\Projects\data-analysis-agent\scripts\mh2_segment_stability_gate.py`。它读取已保存的标签/分群时效、行为基线/分组结果和留存结果，输出 `READY` 或 `EVIDENCE_REQUIRED`；不执行线上写入。

## 使用规则

- 先选人口和行为指标，再从本表选择一个或多个 `READY` 分组；没有 `READY` 元数据不得拼接 `groupBy`。
- 多维分析按业务维度在前、人口分群在后排列。例如 `职业 × 勇1新老` 为 `[career, cohort_20260824_202104]`。
- 使用动态标签或导入分群时，输出必须带实际的 `specifiedClusterDate`；事件日期不能替代标签快照日期。
- `PENDING_METADATA` 只记录业务需求，不是可执行分组。补齐实际请求中的 `tableType`、`subTableType`、`columnName`、标签快照策略并经真实只读请求 `return_code=0` 与总量守恒后，才能改为 `READY`。
- 单次报表临时分档放在该次报告/运行证据中；只有会在后续行为分析中复用的分组才登记到本表。
- 新分组正式启用前，必须用稳定性验收入口完成一次基线守恒、行为交叉、留存 cohort 一致和时效判定；验收 JSON 与输出摘要纳入同一 run evidence 目录。

## 标签与分群时效 Gate

标签/分群的“日期”至少有三种，必须分别记录，不能互相替代：

| 字段 | 含义 | 留存示例 |
| --- | --- | --- |
| `behavior_date` / `cohort_date` | 行为观察日或留存初始 cohort 日 | `2026-08-31` 创角用户 |
| `return_window` | 留存回访日/窗口 | D1 为 `2026-09-01` 的回访 |
| `specifiedClusterDate` | 本次请求实际采用的标签/分群快照日 | 勇1老用户标签快照 `2026-08-31` |
| `tag_last_updated_at` | 标签/分群在数数侧最后一次成功物化/更新的 UTC+8 时间 | `2026-08-31 10:32:13 UTC+8` |

每次使用标签或分群的事件、留存、漏斗或分布请求，运行证据和用户输出都必须带前四项，以及一个时效结论：

| 时效结论 | 条件 | 可否将人口称为请求日的标签/分群 |
| --- | --- | --- |
| `READY_CURRENT` | 已取得请求日对应的 `specifiedClusterDate`，且已确认该快照已完成所需更新 | 可以 |
| `READY_HISTORICAL` | 用户明确要求用较早的已验证快照观察另一日行为，且输出同时写明两个日期 | 不可以；只能称为“使用 S 日快照观察 D 日行为” |
| `EVIDENCE_REQUIRED` | 缺少请求日快照、最后成功更新时间、标签 SQL/更新规则，或更新尚未覆盖请求口径 | 不可以；不得把结果补为 0 或沿用旧快照冒充当前分群 |

### 勇1老用户的当前性规则

`cluster.hero1_old_user` 是每天人工跟进的导入分群。当前 Skill 的**最新已验证** `specifiedClusterDate` 是 `2026-08-27`，不是一个可无限沿用的“最新标签”。

- 用户请求“`2026-08-31` 勇1老用户/纯新用户的行为或留存”时，必须先取得 `specifiedClusterDate=2026-08-31` 的真实分群请求证据及其实际更新时间；若没有，返回 `EVIDENCE_REQUIRED`。
- 标准提醒文案：`勇1老用户分群的最新已验证快照为 2026-08-27，未取得 2026-08-31 的完成快照；不能将结果标为“2026-08-31 勇1老用户/纯新用户”。`
- 仅当用户明确接受历史口径时，才可用 `2026-08-27` 快照分析 `2026-08-31` 行为；标题必须写成：`行为日：2026-08-31；勇1老用户标签快照：2026-08-27（历史快照，非 8/31 当前分群）`。
- 不能因为行为日已经成熟、HTTP 200 或旧请求曾 `return_code=0`，就推断 `2026-08-31` 的分群已更新。

### 数值标签的完整入库要求

一个数值标签要从“能看到”变为“可稳定复用”，必须同时保留两类事实：

1. **标签定义版本**：标签 SQL、计算范围/时间窗、角色主键、更新方式、最后成功更新时间和人数；
2. **分层方案版本**：来源标签、适用人口、每个区间边界、空值策略、是否允许与其他分群交叉，以及实际模型请求的 `groupBy`/区间配置。

用户标签列表只能证明第一类中的部分元数据，不能证明区间或 `groupBy` 调用正确。首次使用时必须保存一份成功模型请求和返回，并验证各区间人数与目标人口守恒；之后这个方案才可标为 `READY`。

## 新增分组的最小入表条件

新增一个“未来会复用”的分组时，登记以下内容即可，不要求新增专用 Python builder：

1. 业务名、人口定义、身份粒度和时间窗；
2. 类型：用户/事件属性、导入分群、动态标签或 SQL 派生；
3. 原生 `groupBy` 完整对象，或 SQL 派生的来源与不可替代原因；
4. 标签快照策略及实际快照日期的输出要求；
5. 至少一份真实只读请求的请求体、原始返回、`return_code=0` 和总量守恒结论；
6. 适用分析类型与不可作出的业务解释。

只有第 1 至 5 项齐全才标记为 `READY`。需要在数数线上新建或修改标签/分群时，先完成业务定义评审并取得单独授权；本表登记本身不创建线上标签。
